# RFC: 발주 AI 워크플로우 시각화 MVP

## 목적

운영자가 AI 발주 제안이 어떤 단계를 거쳐 만들어졌는지 확인하고, 각 단계의 판단 근거를 이해한 뒤 발주를 결정할 수 있게 한다.

이 문서는 다음 구현 세션의 기준 문서다. 구현자는 이 범위를 벗어나는 기능을 추가하지 않는다.

## 사용자 문제

현재 `/orders` 화면에서는 최종 제안 수량과 근거만 확인할 수 있다. 운영자는 수요 예측, 공급 조건 검토, 최종 수량 산정이 어떤 순서로 실행됐는지 확인할 수 없어 제안을 신뢰하거나 수정할 근거가 부족하다.

## MVP 사용자 흐름

1. 운영자가 `/orders`에서 상품을 선택한다.
2. `AI 발주 예측 실행`을 누른다.
3. 화면은 실제 예측 API 응답을 받은 뒤 아래 네 단계의 흐름을 표시한다.
4. 운영자가 단계를 선택하면 그 단계의 실행 메시지를 확인한다.
5. 마지막 단계의 제안 수량을 바탕으로 승인·수정·거절한다.

```text
수요 예측 → 공급 조건 검토 → 최종 발주 제안 → 운영자 결정
```

## 포함 범위

### 화면

- `/orders`에 가로 또는 세로로 연결된 네 개의 워크플로우 노드를 표시한다.
- 노드 이름은 다음으로 고정한다.
  - `수요 예측` (`demand_agent`)
  - `공급 조건 검토` (`supplier_agent`)
  - `최종 발주 제안` (`supervisor`)
  - `운영자 결정` (`operator_decision`)
- 예측 실행 전에는 AI 노드를 `대기`로 표시한다.
- 예측 실행 성공 후에는 API가 반환한 실제 단계 결과를 `완료`로 표시한다.
- 실행 실패 시 AI 노드는 `오류`로 표시하고, 기존 오류 메시지를 함께 노출한다.
- 선택한 노드의 메시지와 입력·출력 요약을 노드 아래 또는 별도 상세 영역에 표시한다.
- `운영자 결정` 노드는 기존 승인·수정·거절 UI와 연결한다.

### API 계약

`POST /api/v1/orders/run-prediction/{product_id}` 응답에 기존 필드는 유지하고 `workflow_steps`를 추가한다.

```json
{
  "purchase_order_id": 50,
  "product_id": 1,
  "suggested_qty": 20,
  "reasoning_summary": "...",
  "execution_logs": ["..."],
  "workflow_steps": [
    {
      "id": "demand_agent",
      "status": "completed",
      "message": "예상 월간 수요량을 산출했습니다."
    },
    {
      "id": "supplier_agent",
      "status": "completed",
      "message": "리드타임 7일 고려 시, 즉시 발주 필요"
    },
    {
      "id": "supervisor",
      "status": "completed",
      "message": "최종 발주 제안 수량 20개 확정"
    }
  ]
}
```

`workflow_steps`는 문자열 로그를 프론트엔드에서 추측해 해석하지 않도록 백엔드가 제공하는 구조화된 결과다. SSE 엔드포인트는 현재 데모용이므로 이번 MVP의 상태 표시 근거로 사용하지 않는다.

## 완료 기준

- 예측 실행 전·성공·실패 상태가 화면에서 구분된다.
- 완료된 각 AI 단계의 실제 메시지가 표시된다.
- 제안 수량과 승인·수정·거절 흐름이 기존처럼 동작한다.
- `workflow_steps`가 기존 예측 API 응답과 함께 반환된다.
- 백엔드 API 응답 테스트와 프론트엔드 빌드가 통과한다.

## 변경 대상

- `app/api/v1/endpoints/orders.py`: 구조화된 `workflow_steps` 반환

- `tests/test_inventory_api.py`: 예측 응답의 단계 구조 테스트
